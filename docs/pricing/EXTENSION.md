# Granot extension transportation pricing integration

Status: implementation specification, October 25, 2026. No pricing runtime or extension change is implemented by this document. The Owner's DOCX sections 1-12 define the pricing policy; [PLAN.md](PLAN.md) defines the independent service boundary. This feature calculates transportation only in `vantage-operations-server`; the extension reads and displays. Existing Enrichment, Tariff Adjustment and Binding Estimate Fee retain their existing behavior.

## Evidence and limits

It proves that the sampled Charges / Forms View document contains all six required inputs. It does not prove every Granot page, carrier, account, weight mode, or future layout has them. No Granot connection or credential file was needed.

The source contains real customer names, phone/email, city/ZIP, record references, and GUID-bearing operational links/actions. Treat those URLs as potentially sensitive session/record material even though the HTML alone does not establish their exact security semantics. Do not commit the HTML, copy its customer values into fixtures, print its full URLs in logs, or execute its scripts/actions. Fixtures must be newly authored structural examples with synthetic data.

## Module and message boundary

Follow the extension's `.cursor/rules/granot-extension-architecture.mdc`:

- Add a DOM-only parser under `src/parsers/granot/`, with typed success/missing/invalid/ambiguous results and per-field provenance labels. Never return full HTML, contact data, arbitrary page links, or auth material.
- Add a proposed read-only `PARSE_TRANSPORTATION_PRICING_INPUTS` message in `src/entrypoints/granot-crm.content.ts`. Keep the entrypoint thin. Existing content scripts run at `document_idle` with `allFrames: true`.
- Extend `src/messaging/tabs.ts`; use `getTargetTabId` and its explicit detached-popup `targetTabId` support. Frame discovery uses `webNavigation.getAllFrames`, falling back to frame zero; inaccessible/no-response frames are reported without treating them as a valid empty move.
- Return complete candidates per document/frame. Do not assemble pickup from one frame and delivery or mileage from another. Unlike current aggregators that select the first found response, pricing must reject multiple distinct candidates. Deduplicate only proven identical observations of the same document; frame identity and document generation belong in the local observation context.
- Put calculation orchestration in a pricing workflow and a new popup workspace; API calls belong in `src/api/`. Keep popup render/state imports out of background code. Initial release is an explicit foreground action, with no unattended pricing or Enrichment apply operation.

Use exact heading/field recognition to establish the supported page. The existing current-form parser recognizes `mpcharge~chargeswc`, but the saved inner HTML does not establish the outer tab URL, iframe tree, or navigation lifecycle. Do not require a Mongo ObjectId in `ORDREF` or a Quoted Granot Priority for pricing; those are unrelated Enrichment gates. Keep any opaque job identity needed to distinguish navigation local and redact it from diagnostics.

## Proposed read/calculate contract

The selected proposed route is `POST /api/v1/pricing/calculate`. Map the parser's actual volume once to `volume_cf`; send only `volume_cf`, `mileage`, `pickup_state`, `pickup_zip`, `delivery_state`, and `delivery_zip`. Numeric decimals are strings, ZIPs remain strings, and states are normalized codes. This is a proposed contract, not an existing endpoint. The recommended default permits up to four fractional digits for CF, mileage and rates, CF/mileage up to 100000, rates up to 1000.0000 USD/CF, and explicit zero. Reject excess precision rather than rounding it; reject numeric wire values, exponent notation, separators, signs, blanks, partial numbers, NaN, Infinity and unsupported units. Format a validated grouped DOM quantity into an ungrouped wire string without losing its precision. Follow SPECIFICATION.md for the exact grammar and limits; Owner approval of these defaults remains pending. USD with final half-up cents is the selected proposed money contract.

The server validates independently and resolves one immutable configuration revision. It applies `billableCf = max(actualCf, 300)`, selects one of eight continuous mileage bands (`<=100`, `>100..300`, `>300..750`, `>750..1250`, `>1250..1800`, `>1800..2500`, `>2500..3000`, `>3000`) and seven billable-CF tiers (`=300`, `>300..500`, `>500..1000`, `>1000..1500`, `>1500..2000`, `>2000..3000`, `>3000`). It looks up one of 56 base-rate cells, then one active pickup surcharge group; only absent active pickup membership allows delivery selection. A configured zero pickup rate still wins. Never stack groups. Missing selected values produce `MILEAGE_RATE_NOT_CONFIGURED` or `STATE_SURCHARGE_NOT_CONFIGURED`, without delivery fallback. Rates and final amount use decimal-safe arithmetic and the approved rounding rule.

The extension must not download a matrix to calculate locally, cache production rules for offline pricing, or recreate those invariants in its tier display. Render the backend's selected keys/labels. The proposed response envelope is `{ok:true,data:{revision_id,activation_version,...}}`. Its data should echo normalized inputs, actual and billable CF, selected mileage band and volume tier, base rate, surcharge source (`PICKUP`, `DELIVERY`, `NONE`), surcharge state/group id/name/rate, final rate, transportation price, currency and calculation time. Return a request correlation id without customer data. Do not substitute Granot's existing charge fields on failure.

## Authentication and deployment boundary

Existing Extension User auth stays in the main server. `src/auth/session.ts` already handles login, `/me` bootstrap, refresh and storage-change invalidation; `src/api/client.ts` currently targets only the main-server base and retries once after 401. Add a deliberate operations API client using the same session provider; do not redirect existing calls or blindly send credentials to a response-supplied URL. A 403 is an authorization denial, not a refresh loop.

The selected integration forwards the incoming Bearer access token from operations to the existing main-server `GET /api/v1/extension/auth/me` on every calculation, using a fixed trusted main-server origin and constant path. That route already checks current active user, email, roles and token version; no new introspection endpoint, signing-key copy or direct `extension_users` access is needed. The operations adapter still needs implementation. Use no redirects, no forwarded cookies/actor/service-secret headers, a three-second deadline, bounded response validation and no positive-result cache, as specified in SPECIFICATION.md. Authority outage/malformed response fails closed with `AUTH_UNAVAILABLE`; authority 401 maps to `UNAUTHENTICATED`. Local logout clears tokens but does not revoke a previously issued token server-side; existing token-version/account changes provide the actual revocation behavior. Matching a JWT signature alone or trusting a client role is insufficient. No readiness `x-api-secret`, developer fallback secret, refresh token, or password belongs in a pricing request to the operations service. Tokens stay in extension-controlled code, never the Granot DOM or page scripts. Configuration mutations require a verified Admin Dashboard Owner; Extension Owner calculation access alone grants no configuration authority.

Recommended calculation access is Owner or Sales, pending Owner confirmation; Customer Service alone is denied, while Sales plus Customer Service is allowed by role union. Current workspace gating grants Sales only Binding Estimate Fee and Customer Service only Tariff, so the new workspace requires explicit role/router changes. Role unions and logout behavior must remain intact. Update the existing user-management documentation when implementing rather than changing role meanings in this specification.

The operations scaffold is deployed at `https://vantage-operations-server.vercel.app`; pricing routes are not implemented. The extension's current `wxt.config.ts` host permissions cover Granot, localhost and the existing main server. When implementing, add exactly `https://vantage-operations-server.vercel.app/*` and configure explicit extension CORS origins on operations; inspect [../environment.md](../environment.md) before adding configuration names. Do not assume host permission or CORS authenticates a user. Chrome MV3 and Firefox MV2 builds both need verification.

## Display, freshness and failure behavior

The new internal workspace should show the observed pickup/delivery state and ZIP, mileage, actual CF, billable CF/minimum applied, selected band/tier, base rate, surcharge source/state/group/rate, final rate per CF, transportation amount, currency, revision and calculation time. Label it "Transportation price"; display the ancillary exclusions clearly enough to avoid presenting it as a full quote. Owner's illustrative example amounts are test data only.

Use explicit states: no supported form, incomplete/invalid inputs, ambiguous form, ready, calculating, calculated, stale, sign-in required, forbidden, and unavailable/configuration error. Calculate stays disabled until exactly one complete valid snapshot exists. Structured API errors distinguish missing configuration from invalid inputs and connectivity problems; offer a fresh read/retry, never zero-price success.

Bind each request to tab id, frame/document generation, a normalized six-input fingerprint and an increasing local request sequence. Re-read before sending and after receiving. Discard late responses when any binding changes. Any input/DOM change, frame navigation/removal, target-tab change, auth loss, failed recalculation, or detected policy revision change immediately removes current-price status and disables copying a current result. An old result may be shown only as clearly stale context. Do not display an old successful result alongside an unlabeled current failure.

Use DOM mutation observation plus input/change listeners while the workspace is open; direct script assignments may not emit events, so always compare a fresh snapshot before calculate/copy and on visibility bootstrap. Closing/reopening the popup starts with a new read, not persisted result state. Revision freshness cannot be guaranteed indefinitely without backend revalidation; recalculate on demand and show the revision/time. Agree on any maximum age before launch. A response remains a price at its recorded revision, never a guaranteed forever-current rate.

Initial release permits display and explicit copying of a labeled breakdown after a freshness check. Do not write `I1TOTAL`, `I1PERCFLBS`, discounts, Others/Extra fields, invoke Submit Charges, book a job, or dispatch Granot field-change events. Granot writeback needs a separate Owner request and exact field/unit/recalculation/approval specification. Existing Binding Estimate Fee writes are not authorization for pricing writeback.

Keep parsed inputs/results in memory. Existing `granot-sync:popup-state-v1` persists preferences only and must not gain snapshots. Log parse outcome codes, missing field names and safe correlation/revision identifiers; exclude full page URLs, DOM dumps, customer contacts and auth tokens. Result retention on the server requires the separate policy decision in PLAN.md.

## Fixtures and acceptance

Author minimal synthetic HTML fixtures preserving the heading row, nested address columns, form name, Initial Price CF row and Distance cell. Use invented city names, safe synthetic ZIPs and no real customer/reference/action URLs. Parse detached DOM with scripts inert; never load the saved source into a browser as an executable page.

Parser cases: NBSP/whitespace; decimal CF/mileage; leading-zero ZIP; optional ZIP+4 per approved policy; missing/invalid state, ZIP, distance or CF; pounds-only mode; duplicate conflicting forms/cells; misleading summary/inventory/rate values; nested-table text; swapped location columns; unrelated maps links; scripts attempting instructions. Assert field provenance and absence of customer data in parser results and logs.

Transport/workflow cases: complete child frame with empty top frame; inaccessible frame; zero responses; distinct candidate conflict; detached target tab; tab switch/navigation while HTTP is pending; out-of-order responses; mutation during calculation/copy; storage logout and visibility bootstrap; 401 refresh success/failure, 403, network/timeout, malformed envelope and missing-rate errors. Assert that no test dispatches a write message or touches charge fields.

Server contract cases belong in the operations repo: every exact mileage/volume edge and just-above decimal; below-minimum CF; approved zero policy; both qualifying states; inactive pickup group; zero pickup rate; missing pickup tier with qualifying delivery; all 56 matrix positions; decimal rounding; revision consistency and authorization denial. Extension tests verify rendering the server's result rather than implementing the pricing rules again. Owner DOCX examples A/B are explicit offline illustrative fixtures, never production seeds.

When implementation lands, run the extension's `pnpm compile` plus focused parser/workflow/transport tests and both browser builds; run operations `pnpm check` for server runtime changes. A controlled browser pilot must confirm frame shape, input freshness and CF/pounds behavior on representative approved Granot pages, comparing with Owner manual answers. Tests remain offline until that pilot is explicitly arranged.
